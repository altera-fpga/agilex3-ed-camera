## Building the software

Call `quartus_py scripts/build_niosv_sw.py`, optionally passing in a `--clean` argument to
destroy build artifacts, and optionally an `--update_sof` to update the generated .sof file
without a full recompile.

This will also generate `.clangd` and `.clang-format` files for editor configuration. It is
highly recommended to use the `clangd` language server if working on the source code, available
as an extension or easy integration on virtually every modern IDE.

The board support package (BSP) and hardware abstraction layer (HAL) are stable if the hardware
(VDS subsystems) does not change. Otherwise, you must use the `--clean` flag to regenerate.

## Software project structure

The raw C/C++ source code lives under `app`.

The BSP and HAL generated by `niosv-bsp` live in `gen/sw/bsp`. This includes drivers from
IPs included in the hardware subsystems. The BSP script `bsp_commands.tcl` is used to
configure the BSP, such as picking between newlib and picolibc.

Refer to the [Nios V Software Developer Handbook](https://docs.altera.com/r/docs/743810/current) for
full details about the HAL and BSP flow.

`niosv-app` creates a CMakeLists.txt under `gen/sw/app`. This
contains references to the original C/C++ files here, using relative paths. These files are NOT
copied over to `gen/sw/app`.

The combination of `niosv-bsp` and `niosv-app` generates a full standalone CMake project, with
`gen/sw/app/CMakeLists.txt` serving as the master build configuration.

The build directory lives in `gen/sw/build`. This houses both the output `app.elf`, the corresponding
`niosv_subsystem_cpu_ram.hex` (which is automatically copied into `mem_init/niosv_subsystem_cpu_ram.hex` if
using the provided script), an `app.elf.objdump`, and a `compile_commands.json` for clangd integration.
